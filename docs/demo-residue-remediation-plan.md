# MVP 演示残留修复规划

> 状态：待执行  
> 目标：清除会造成“界面显示成功、实际未写入系统”的 Demo 残留，使 MVP 的每个可见入口与真实能力保持一致。  
> 范围基线：以当前 `AppV2`、FastAPI 后端和 SQLite 数据库为准；旧 Demo 文档只作为历史参考，不作为运行时契约。

## 1. 结论与修复原则

当前系统不是整体 Demo：登录、项目、阶段、任务状态机、提交验收、候选提取和任务详情内的 AI 草稿已经接入后端。

但正式入口仍混用了三类实现：

1. **真实实现**：调用后端 API，服务端鉴权并持久化。
2. **本地演示实现**：只修改 React 内存，刷新后消失。
3. **提示型假实现**：按钮仅弹出“成功”提示，实际没有业务动作。

修复不追求一次性把所有远期功能都做完。处理策略只有两种：

- MVP 范围内的功能：接入真实后端，完成持久化、权限和异常处理。
- MVP 范围外的功能：明确标注“暂未开放”并禁用入口，不能继续伪装成已完成。

## 2. 优先级定义

| 优先级 | 判定标准 | 处理要求 |
| --- | --- | --- |
| P0 | 会产生假任务、假状态或破坏核心任务闭环 | 第一批修复，未完成不得继续扩展功能 |
| P1 | 同一业务在不同页面状态不一致，或 AI 能力被演示逻辑替代 | P0 后立即处理，纳入 MVP 验收 |
| P2 | 非核心模块只保存在前端，刷新丢失或多人不可见 | 按 MVP 范围选择真实接入或关闭入口 |
| P3 | 旧源码、旧文档、命名和配置残留，当前不直接影响运行 | 核心链路稳定后清理 |

## 3. 修复清单

### P0-1：统一候选任务创建链路

**当前问题**

- 新版候选提取使用后端 `Candidate` API。
- 首页候选、项目 AI 对话候选和个人 AI 对话候选仍会进入旧 `CandidateReview`。
- 旧流程只向前端 `tasks` 数组追加任务，没有数据库记录，也没有 `apiStatus`、`version` 和审计记录。

**影响**

- 刷新后任务消失。
- 任务详情无法正确执行开始、提交和验收动作。
- 页面提示“正式创建”，但系统中没有正式任务。

**实现路径**

1. 删除或停止调用旧 `CandidateReview` 的本地创建逻辑。
2. 项目聊天或个人 AI 识别候选时，先调用 `POST /api/candidate-extractions`，或新增单条候选创建接口。
3. 候选审核统一使用：
   - `PATCH /api/candidates/{id}` 保存调整；
   - `POST /api/candidates/{id}/confirm` 正式建任务；
   - `POST /api/candidates/{id}/ignore` 忽略候选。
4. 确认成功后使用服务端返回的 `TaskRead` 更新前端，禁止手工拼装 `Task`。
5. 移除 `initialCandidates` 对正式候选列表的注入；如需演示数据，只能由后端种子数据生成。

**验收标准**

- 从所有候选入口创建的任务都能在刷新后保留。
- 新任务具有服务端 ID、版本号、负责人、验收人和初始状态。
- 新任务可完整执行“接收/开始 → 提交 → 验收”。
- 重复确认不会创建两条任务。

### P0-2：修复开放任务认领

**当前问题**

- 开放任务来自静态 `openTasks`。
- “认领任务”只复制到本地任务数组，没有服务端写入。

**实现路径**

方案 A（纳入 MVP，推荐）：

1. 在任务模型增加或复用“开放认领”状态及可认领条件。
2. 新增 `POST /api/tasks/{id}/claim`，服务端检查任务仍未被认领。
3. 在同一事务内写入负责人、状态历史和审计记录。
4. 前端认领成功后重新读取任务列表。
5. 对并发认领返回 `409`，页面提示“任务已被其他成员认领”。

方案 B（不纳入 MVP）：

1. 隐藏“开放任务”标签页及相关数量。
2. 删除静态任务注入和成功提示。
3. 等后端模型确定后再重新开放。

**验收标准**

- 认领结果刷新后仍存在，其他账号可见。
- 同一任务不能被两个人同时认领。
- 不存在只在当前浏览器中出现的任务。

### P0-3：禁止提示型假成功

**当前问题**

部分按钮执行后只显示“已保存”“已通知”“已打开”“已开始运行”，但没有 API 请求或可验证结果。

**实现路径**

1. 建立所有可写按钮清单，标记为 `REAL`、`READ_ONLY`、`DISABLED`。
2. `REAL` 按钮必须等待服务端成功响应后才能显示成功提示。
3. 尚无后端能力的按钮必须禁用，并显示“暂未开放”，不得使用成功 Toast。
4. 请求失败时保留用户输入，显示可重试错误；不得关闭弹窗并伪装完成。

**验收标准**

- 任意“成功”提示都有对应的服务端记录或可观察结果。
- 断开后端后，所有写操作均明确失败，不出现成功提示。

### P1-1：让 AI 执行中心使用真实 AgentRun

**当前问题**

- 任务详情的 AI 草稿调用真实 `/agent-runs` API。
- `/agent` 页面仍根据任务状态拼装运行记录、进度、步骤和产物名称。
- “模拟完成”“补充要求”“重试”“停止执行”只改变本地状态。

**实现路径**

1. 增加可按当前用户查询的 `GET /api/agent-runs`，支持状态和项目筛选。
2. 执行中心直接展示服务端 `AgentRun`，不再从 `Task` 推导伪运行记录。
3. 复用任务详情已经验证的 AI 重做流程。
4. 若 MVP 的 AgentRun 是同步执行：
   - 页面只展示真实开始时间、结束时间、模式和草稿；
   - 不显示无法证明的实时百分比和步骤动画。
5. 若需要停止/重试，则先实现后端状态机和幂等接口；否则禁用这两个按钮。
6. 删除“模拟完成并提交确认”和硬编码历史运行。

**验收标准**

- 任务详情与执行中心显示同一个 Run ID、执行模式和结果版本。
- 刷新或换账号后状态一致。
- MOCK、LIVE、FALLBACK 标签来自服务端记录。

### P1-2：处理项目 AI 协作的演示聊天

**当前问题**

- 消息通过 `setTimeout` 返回固定回答。
- 会话、成员、消息和候选任务都只存在于页面内存。
- 页面宣称读取项目任务、会议和资产，但实际未建立对应检索链路。

**实现路径**

分两步实施：

**第一步：诚实降级**

1. 在真实接口完成前，将输入区标记为“项目 AI 协作预览”。
2. 禁止产生可提交候选和“已邀请成功”等业务结果。
3. 保留只读界面用于确认布局，不得伪装为真实 AI。

**第二步：真实接入**

1. 增加项目会话、消息、成员权限和上下文引用的数据模型。
2. 提供项目会话列表、创建会话、读取消息和发送消息 API。
3. 服务端按项目成员权限装载项目任务；会议和资产尚未接入时不得宣称已读取。
4. AI 输出生成候选时进入统一 Candidate 流程。
5. 保存模型、Prompt 版本、上下文引用、执行模式和耗时。

**验收标准**

- 会话刷新后仍存在，只有项目成员能读取。
- AI 回答不是固定文本，且能指出实际引用的项目任务。
- 未接入的数据源不会显示为“已连接”。

### P1-3：统一任务状态变更入口

**当前问题**

任务详情已经使用后端状态机，但看板拖动、执行中心停止、部分提醒和协作留言仍会直接修改本地 `Task`。

**实现路径**

1. 禁止前端直接构造业务状态变化。
2. 看板拖动映射为已有 `performTaskAction`；没有合法状态动作时禁止放置。
3. 服务端返回最新任务和版本，前端以返回值替换本地对象。
4. 冲突、越权和非法转换分别展示明确错误。

**验收标准**

- 所有状态变化都有状态历史。
- 刷新后看板和任务详情状态一致。
- 非负责人或非验收人不能绕过权限改变状态。

### P2-1：知识、资产、求助、通知和设置模块分流

**当前问题**

这些页面多数仍使用 `initial*` 静态数据和 React 内存，没有对应后端接口。

**实现路径**

逐模块作产品决策，不允许维持“半真半假”：

| 模块 | 若纳入 MVP | 若不纳入 MVP |
| --- | --- | --- |
| 智能求助 | 建 HelpRequest、专家转交、解决和知识沉淀 API | 保留只读示例，关闭发布和状态变化 |
| 知识空间 | 建页面、版本、自动保存和发布快照 API | 标记预览，关闭新建、编辑和发布 |
| 资产库 | 建元数据、上传、下载和权限 API | 只读展示，关闭上传和“打开原文件” |
| 通知中心 | 从服务端读取通知并保存已读状态 | 只显示系统级固定提示，不宣称已通知他人 |
| 能力库/Skill | 建真实运行和运行记录 | 禁用“开始运行”，保留能力说明 |
| 团队与设置 | 建团队成员、邀请、偏好设置 API | 只读展示当前登录身份，关闭保存和邀请 |

**验收标准**

- 每个模块都有明确的 `REAL` 或 `PREVIEW` 标识。
- PREVIEW 模块没有会产生业务误解的写按钮。
- REAL 模块刷新、换浏览器和换成员后数据一致。

### P2-2：任务协作留言和通知持久化

**当前问题**

- 任务留言和 @成员只保存在任务详情组件内存。
- “对方已收到通知”没有服务端依据。

**实现路径**

1. 增加任务活动/评论模型和 API。
2. 服务端解析并校验被提及成员，创建通知。
3. 评论、状态历史和系统事件按时间统一展示。
4. 成功提示以服务端返回的通知对象为准。

**验收标准**

- 刷新后留言保留。
- 被提及账号能够看到对应通知并跳转到任务。

### P3-1：清理旧 Demo 代码和文档边界

**当前问题**

仓库仍包含旧 `App.tsx`、`store.tsx`、`data.ts`、Demo 构建提示和旧交付说明。它们当前未被 `main.tsx` 引用，但会增加误改、误引用和理解成本。

**实现路径**

1. 确认没有生产代码引用后，将旧 Demo 源码移入 `archive/demo-baseline/` 或从当前开发分支删除。
2. `workHubData.ts` 只保留纯展示枚举和无业务副作用的视觉数据。
3. 所有业务实体改由 API 类型生成，不再维护第二套状态枚举。
4. 在 README 标明当前真实能力、预览能力和启动配置。
5. CI 增加检查，禁止生产入口重新引用 `store.tsx`、`data.ts` 或旧 `App.tsx`。

## 4. 分阶段实施顺序

### 阶段 0：冻结入口与建立真实性清单

- 暂停新增外围功能。
- 枚举所有可点击写操作。
- 为每个入口标记真实 API、只读或禁用。
- 增加“断开后端不得显示成功”的基础测试。

交付物：按钮真实性清单、范围确认、回归用例。

### 阶段 1：修复假任务

- 统一 Candidate 创建。
- 处理开放任务认领。
- 删除前端手工拼装正式任务的代码。

交付物：所有任务均来自数据库，刷新不丢失。

### 阶段 2：统一任务和 AI 状态

- 看板状态变更全部走服务端。
- 执行中心读取真实 AgentRun。
- 移除模拟完成、模拟重试、模拟停止。

交付物：任务详情、看板、执行中心状态一致。

### 阶段 3：处理项目 AI 协作

- 先进行诚实降级。
- 再实现真实项目会话、消息和受限上下文。
- 候选输出接入统一审核流程。

交付物：可持久、可鉴权、可审计的项目 AI 对话。

### 阶段 4：外围模块取舍

- 逐项决定知识、资产、求助、通知、能力、团队和设置是否进入 MVP。
- 进入 MVP 的完成后端闭环；不进入的关闭写入口。

交付物：无半实现、无假成功的功能边界。

### 阶段 5：配置和旧代码收口

- 本地开发允许 Demo Seed；正式验收关闭 Demo Seed。
- 固化 Ollama Live 启动方式。
- 清理或归档旧 Demo 源码。
- 更新 README、发布清单和接口文档。

交付物：可重复启动、可重复验收的 MVP 基线。

## 5. 开发与验收底线

以下条款属于阻断性底线，违反任意一条不得标记阶段完成。

### 5.1 数据底线

1. **正式业务数据必须由后端生成和持久化。**
2. 写操作成功后刷新页面，结果必须仍存在。
3. 换浏览器或换账号后，数据应按权限一致可见。
4. 前端不得自行生成正式任务状态、版本号或审计结果。
5. 失败请求不得先乐观显示不可撤回的成功结果。

### 5.2 状态机底线

1. 任务状态只能通过服务端动作接口改变。
2. 负责人、验收人和普通成员权限必须在服务端校验。
3. 非法转换必须失败，不能由前端静默修正。
4. 状态、提交物、贡献和审计需要事务化写入。
5. 幂等请求重复执行不得产生重复任务、重复提交或重复贡献。

### 5.3 AI 底线

1. AI 输出必须标识 `LIVE`、`MOCK` 或 `FALLBACK`。
2. Mock 和 Fallback 不得冒充真实 Ollama 调用成功。
3. 固定文案或 `setTimeout` 结果不得显示为“AI 已分析”。
4. AI 创建的内容必须先进入人工确认，不得绕过门禁成为正式任务或资产。
5. 每次真实调用必须记录模型、Prompt 版本、耗时、结果和失败原因。
6. 页面宣称读取某项上下文前，服务端必须确实读取且用户具备权限。

### 5.4 交互底线

1. 没有实现的功能必须明确禁用或标注“暂未开放”。
2. 成功提示必须对应已完成且可验证的业务结果。
3. 请求处理中禁止重复提交；失败后必须允许重试。
4. 关键操作必须有加载、成功、失败和冲突状态。
5. 不得用静态演示数据填补真实列表的空白状态。

### 5.5 配置与发布底线

1. 正式验收环境必须设置强随机 `JWT_SECRET`。
2. 正式验收必须设置 `SEED_DEMO_DATA=false`。
3. Ollama 验收必须显式使用 `AI_MODE=live`、`AI_PROVIDER=ollama`。
4. 健康检查不得泄露密钥，但应能确认当前 AI 模式和 Provider 是否符合验收配置。
5. 正式构建不得引用旧 Demo Store 或旧入口。

## 6. 自动化防回归要求

至少增加以下测试：

1. **刷新持久化测试**：每个真实写操作完成后刷新并核对结果。
2. **断后端测试**：停止后端后点击写按钮，不得出现成功提示。
3. **多账号测试**：负责人提交、验收人审批、普通成员越权失败。
4. **候选统一测试**：从会议、聊天、项目 AI 和首页入口创建的候选都进入同一 API。
5. **状态一致性测试**：任务详情、任务池、看板和执行中心显示一致。
6. **AI 模式测试**：LIVE、MOCK、FALLBACK 的标识和日志严格对应。
7. **静态扫描**：正式页面中新增 `setTimeout` 模拟业务完成、硬编码 `run-history-*`、仅 `notify("已成功")` 的写按钮时使 CI 失败。

## 7. 阶段完成定义（Definition of Done）

每个阶段只有同时满足以下条件才能提交：

- 功能代码与接口契约一致。
- 后端权限和异常分支有自动化测试。
- 前端完成正常、加载、失败、冲突和空状态。
- 浏览器完整走通目标流程。
- 刷新后结果不丢失。
- 未实现入口已经关闭，不存在假成功。
- 构建、后端测试和端到端回归通过。
- README 和发布清单同步更新。
- 每阶段单独提交并推送，提交说明指出已清除的 Demo 残留和仍保留的预览范围。

## 8. 建议首先执行的三个改动

1. 将所有 `openCandidate(...)` 入口迁移到真实 Candidate API，并删除旧 `CandidateReview` 创建任务逻辑。
2. 暂时隐藏“开放任务认领”和 `/agent` 中的模拟写按钮，避免继续产生假状态。
3. 将项目 AI 协作输入区标记为预览或暂时只读，直到真实项目会话接口完成。

完成这三项后，即使外围模块尚未开发完，系统也不会再把演示动作误报为正式业务结果。
