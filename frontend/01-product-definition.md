# 全意 AI Task OS｜产品定义 V1.0

## 1. 产品名称

**全意 AI Task OS**

内部代号：**QY Task OS**

## 2. 一句话定义

面向全意内部小团队的 AI 原生任务协作系统，将聊天、会议和 Agent 工作过程中的任务自动拾取出来，经人工确认后，完成任务分配、执行、跟进、求助、验收与贡献记录。

## 3. 产品定位

它不是传统待办工具，也不是 OA、CRM 或飞书替代品，而是：

> 一个以“任务”为核心，让人、AI 与外部协作对象进入同一套工作流的内部任务操作系统。

## 4. 核心问题

1. 任务散落在聊天、会议和口头沟通中，容易遗漏。
2. CEO/负责人承担了大量任务分配、解释和追问成本。
3. 员工接到任务后，缺少背景、执行路径和验收标准。
4. 当前可执行任务与等待客户任务混在一起，造成注意力噪音。
5. AI参与了工作，但没有正式进入任务系统。
6. 问题解决依赖个人，知识难以沉淀。
7. 贡献缺少统一记录，主动认领与答疑行为不可见。

## 5. 产品目标

### 5.1 自动发现任务
从聊天、会议、CLI、Codex 和其他授权工作上下文中识别潜在任务。

### 5.2 降低任务管理成本
自动补全任务背景、执行建议、风险、依赖和跟进节点，减少负责人逐项解释与追问。

### 5.3 让 AI 成为正式执行者
任务支持三种执行方式：人工执行、AI执行、人机协作。

### 5.4 对外部等待降噪
将“当前可执行”和“等待外部”明确分区。等待外部事项不占用日常注意力，但系统持续负责提醒。

### 5.5 形成组织知识与贡献记录
任务、求助、会议和 Agent 执行结果可以沉淀为知识，并形成轻量贡献积分。

## 6. 目标用户

| 角色 | 主要诉求 |
|---|---|
| CEO/负责人 | 快速下达任务、掌握项目、减少追问、确认关键任务 |
| AI产品经理 | 获取完整背景、推进任务、调用AI、处理跨角色协作 |
| 产品运营 | 跟踪客户事项、协调内外部、管理等待外部任务 |
| 全栈工程师 | 接收清晰需求、调用Codex、提交执行结果 |
| AI Agent | 通过CLI/API读取、执行和更新任务 |
| 外部联系人 | 不登录系统，由内部成员维护其事项和进度 |

## 7. 核心设计原则

### 7.1 自动拾取，人工确认创建
第一阶段所有候选任务必须经过人工确认。后续演进：全部人工确认 → 明确规则自动创建 → 高置信度自动创建，保留撤销和审计。

### 7.2 AI建议，人做关键判断
AI负责识别、补全、拆解、推荐和执行；人负责确认、判断、验收和商业决策。

### 7.3 当前可执行优先
默认首页只突出当前可以推进的工作。等待外部事项被折叠，只有临期、逾期或状态变化时重新提升注意力。

### 7.4 AI身份透明
所有结果必须标注执行模式、执行Agent、人工确认节点和执行日志。

### 7.5 游戏化服务于推进
积分只记录明确行为，不做复杂价值判断，不直接绑定绩效。

## 8. 核心对象
项目、阶段、任务、候选任务、子任务、内部成员、AI Agent、外部联系人、外部依赖、会议、求助、知识条目、贡献记录、执行日志。

## 9. 产品边界

### V1要做
- 项目与任务基础管理
- 聊天/会议候选任务识别
- 人工确认创建
- 当前可执行/等待外部分区
- 人工、AI、人机协作三种执行模式
- AI执行建议
- AI执行状态与人工验收
- CLI/API基础能力
- 求助与轻量知识沉淀
- 基础积分与贡献记录

### V1不做
- OA、考勤、报销、复杂审批
- 完整CRM、客户登录端
- 完整绩效系统
- 文件管理平台
- 替代飞书/微信
- 无确认的高风险自动派发

## 10. V1成功指标

| 指标 | 目标含义 |
|---|---|
| 候选任务确认率 | AI识别是否准确 |
| 候选任务误识别率 | 自动拾取噪音是否可控 |
| 任务遗漏数 | 是否降低遗漏 |
| 负责人主动追问次数 | 是否降低管理成本 |
| 等待外部逾期率 | 是否减少遗忘 |
| AI建议使用率 | 建议是否有效 |
| AI任务验收通过率 | AI执行是否可靠 |
| 求助平均解决时间 | 是否提升协作效率 |
| 每周活跃成员数 | 系统是否进入真实工作流 |

优先验证：任务遗漏是否减少、泉哥主动追问是否减少、从聊天到正式任务的转化是否顺畅。
