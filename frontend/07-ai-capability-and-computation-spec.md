# 全意 AI Task OS｜AI 能力、人工审核与计算规则开发规格 V1.0

> 文档状态：开发实施版  
> 适用范围：当前 Demo 预览及后续正式后端、AI 服务、数据服务与第三方连接器开发  
> 核心目标：明确每个产品场景分别由人工、数据、规则、算法、Embedding、RAG、模型、Agent 和基础设施中的哪些能力完成，以及它们之间的调用顺序、写入权限、失败降级、成本策略和验收标准。

---

## 0. 开发结论摘要

全意 AI Task OS 不能实现为“任务系统 + 一个大模型接口”，应实现为九层协作系统：

1. **人（Human-in-the-loop）**：负责确认、判断、授权、验收、发布和例外处理。
2. **业务数据（Data）**：记录项目、任务、人员、会议、聊天、资产、知识、运行和审计事实。
3. **业务规则（Rules）**：负责权限、状态机、人工门禁、提醒阈值、积分和不可违反的业务约束。
4. **确定性算法（Algorithms）**：负责进度、排序、匹配、置信度、风险、负荷、去重和统计。
5. **Embedding / 语义能力**：负责语义召回、相似度、聚类和候选集生成。
6. **RAG**：在权限范围内检索内部知识，为模型提供可追溯上下文。
7. **模型（Models）**：负责自然语言理解、信息抽取、总结、生成、分析和解释。
8. **Agent / Tools**：负责真正调用工具、编写代码、生成文件、执行工作和回传过程。
9. **平台治理（Platform）**：负责模型路由、任务编排、缓存、队列、成本、评测、监控、安全和版本管理。

基本原则：

- **AI 可以建议，不能越过人工门禁。**
- **数学结果由数据和算法产生，模型只解释，不拍数。**
- **状态、权限、积分和正式发布由规则控制，不能由模型直接决定。**
- **RAG 只补充上下文，不代替业务数据库。**
- **先使用零模型/规则/小模型，只有复杂或高风险任务才升级到推理模型。**
- **所有 AI 结果必须保存来源、模型版本、输入范围、输出、置信度、人工操作和成本。**
- **AI 执行完成不等于业务完成；业务完成必须经过人工验收或明确配置的低风险自动规则。**

## 1. 能力职责边界

| 能力 | 适合处理 | 禁止或不建议处理 |
|---|---|---|
| 人 | 候选确认、任务分发、商业判断、AI结果确认、验收、知识发布、权限批准、例外处理 | 不应承担机械汇总、重复检索、常规提醒 |
| 数据 | 保存事实、版本、关系、历史事件、权限、反馈 | 不产生主观结论 |
| 规则 | 状态流转、强制字段、权限、提醒、积分、人工门禁、审计 | 不理解长文本语义 |
| 算法 | 加权计算、排序、匹配、去重、置信度、风险、负荷 | 不生成长篇业务内容 |
| Embedding | 语义检索、相似任务、相似知识、聚类、候选召回 | 不直接生成答案，不直接决定是否创建任务 |
| RAG | 查找企业知识、项目资料、会议证据、历史案例并提供引用 | 不负责精确状态和权限事实的最终判断 |
| 模型 | 抽取、分类、总结、拆解、生成、解释、复杂分析 | 不直接修改权限、积分、验收结果和正式发布状态 |
| Agent | 调用工具、生成产物、执行代码/文档/研究任务 | 不直接把业务任务置为 DONE |
| 平台治理 | 模型路由、队列、缓存、成本控制、评测、日志、告警 | 不承载具体业务判断 |

### 1.1 必须由人完成或确认的动作

V1 以下动作必须有人工节点：

- 候选任务成为正式任务。
- 会议行动项统一下发。
- 被分配成员确认接收、退回补充或申请改期。
- AI 推荐负责人后的正式派发。
- AI 执行结果确认。
- 任务验收通过或退回修改。
- 关键任务取消、删除、负责人变更。
- 任务转为等待外部时确认等待对象和恢复动作。
- 求助是否真正解决。
- 求助、任务或会议内容沉淀为正式知识。
- 知识页面发布为稳定资产快照。
- 贡献积分的特殊调整。
- Agent 新增权限、扩大项目读取范围或使用高风险工具。
- 高成本或高风险模型调用超过预算阈值时的继续授权。

### 1.2 人工审核状态建议

统一使用以下审核对象，不要在各模块自行发明状态：

```text
DRAFT                草稿
AI_PROCESSING         AI处理中
PENDING_HUMAN_REVIEW  待人工审核
CHANGES_REQUESTED     已退回修改
APPROVED              已审核通过
PUBLISHED             已正式发布/生效
REJECTED              已拒绝
CANCELED              已取消
```

审核记录必须包含：

```text
review_id
object_type
object_id
review_type
requested_by
reviewer_id
status
ai_output_version
decision_note
created_at
decided_at
```

## 2. 厂商中立的模型分级与经济性策略

### 2.1 不把具体厂商型号写死在业务代码中

业务代码只能请求能力等级，例如 `FAST_EXTRACT`、`GENERAL`、`REASONING`，由 Model Gateway 映射到实际供应商和模型。

```text
业务服务
→ Model Gateway
→ 根据任务类型、风险、上下文长度、质量要求、预算和实时负荷选择模型
→ 返回统一结构
```

模型注册表至少包含：

```text
model_id
provider
capability_tier
modalities
context_limit
structured_output_support
tool_call_support
average_latency_ms
input_cost_per_million
output_cost_per_million
internal_or_external
data_retention_policy
enabled
```

### 2.2 六级处理策略

| 等级 | 名称 | 典型实现 | 用途 | 成本策略 |
|---|---|---|---|---|
| T0 | 无模型 | SQL、规则、状态机、定时任务 | 统计、提醒、权限、积分、进度 | 最低成本，优先使用 |
| T1 | 传统算法 | BM25、时间解析、相似度、排序模型 | 搜索、去重候选、匹配、风险评分 | 低成本、稳定 |
| T2 | 小模型 | 约 3B～8B 指令模型或低价API模型 | 分类、短摘要、字段抽取、标签 | 高频默认层，可批处理 |
| T3 | 通用模型 | 约 14B～32B 或中档API模型 | 任务补全、纪要、RAG回答、建议 | 主力质量层 |
| T4 | 推理模型 | 强推理API或较大推理模型 | 复杂规划、冲突判断、关键分析 | 仅在必要时升级 |
| T5 | 专用模型 | ASR、Embedding、Reranker、OCR、代码Agent | 语音、检索、重排、代码执行 | 按模态独立选型 |

这里的参数规模只代表能力层级，不绑定具体开源或商业厂商。正式选型必须用全意真实样本进行同一套评测后确定。

### 2.3 默认模型路由

| 任务 | 默认等级 | 升级条件 |
|---|---|---|
| 是否存在任务的初筛 | T2 | 语义含糊、多人多任务、低置信度时升 T3 |
| 标题/负责人/时间/交付物抽取 | T2 | 字段冲突、相对时间复杂、负责人不明确时升 T3 |
| 短会议摘要 | T2/T3 | 超长会议、分歧多、决策复杂时升 T4 |
| 完整会议纪要 | T3 | 高层决策会、合规敏感内容升 T4 |
| 任务背景和验收标准补全 | T3 | 高风险项目或资料冲突升 T4 |
| 任务拆解 | T3 | 跨部门、复杂技术或长周期任务升 T4 |
| RAG问答 | T3 | 低检索置信度、资料冲突、关键决策升 T4 |
| 风险解释 | T3 | 风险分高、影响多个里程碑升 T4 |
| 日报/周报 | T2/T3 | 高管汇报或跨项目归因升 T4 |
| 代码修改 | T5代码Agent | 涉及架构、安全、数据迁移时使用高推理编码Agent |
| 状态流转、进度、提醒、积分 | T0 | 不升级，不调用模型 |

### 2.4 路由决策分

```text
complexity_score =
0.25 × 上下文长度等级
+ 0.20 × 参与角色数量等级
+ 0.20 × 输出复杂度等级
+ 0.20 × 业务风险等级
+ 0.15 × 歧义/冲突等级
```

- `0～29`：T2
- `30～64`：T3
- `65～100`：T4
- 任何涉及权限扩大、正式发布、验收、资金、合同或删除的任务，无论分数多少，都必须人工确认。

### 2.5 级联调用，兼顾成本与质量

不建议所有请求直接调用最强模型。采用级联：

```text
规则/算法预处理
→ 小模型生成结构化结果
→ 计算字段置信度和规则完整度
→ 高置信度：进入人工审核
→ 中置信度：通用模型复核
→ 低置信度或高风险：推理模型复核
→ 仍有冲突：要求人工补充
```

成本优化措施：

- 能用 T0/T1 完成的任务禁止调用模型。
- 聊天先按线程和时间窗口聚合，再批量调用，不逐条消息调用。
- 模板化系统提示词，避免每次重复发送大量固定文本。
- 先用 Embedding/BM25 取小范围上下文，再交给模型，禁止全库塞入上下文。
- 对相同输入、同一知识版本和同一 Prompt 版本使用语义缓存。
- 日报、周报、知识索引等非实时任务走异步低优先级队列。
- 长文先分段摘要，再由主模型合并，避免一次超长上下文。
- 只在需要时返回长解释；后台抽取默认返回 JSON。
- 配置单用户、单项目、单组织的日/月预算和高成本调用告警。
- 保存各模型在真实场景的准确率、延迟和单次成本，按周调整路由。

### 2.6 模型选择不能只看价格

每个候选模型统一测量：

```text
综合效用 =
0.40 × 任务质量
+ 0.20 × 结构化输出稳定性
+ 0.15 × 延迟表现
+ 0.10 × 中文理解
+ 0.10 × 工具调用稳定性
+ 0.05 × 数据合规
- 成本惩罚项
```

不同场景使用不同门槛，不能用一个总榜决定全部任务。

## 4. 核心计算规则

### 4.1 任务进度

优先使用交付检查点：

```text
task_progress = Σ(checkpoint_weight × checkpoint_completion)
```

约束：

- 检查点权重合计必须等于 1。
- 检查点完成度只能来自实际状态或人工更新。
- 模型可建议检查点和权重，但负责人确认后才能生效。
- `WAITING_EXTERNAL`、`BLOCKED` 不回退进度，只冻结。
- `WAITING_HUMAN_CONFIRMATION` 上限 90%。
- `WAITING_REVIEW` 上限 95%。
- 只有验收通过可达到 100%。

没有检查点时使用状态区间，而不是虚构精确百分比：

| 状态 | 默认进度 |
|---|---:|
| TODO | 0 |
| IN_PROGRESS | 由人工或子任务计算，范围5～85 |
| WAITING_HUMAN_CONFIRMATION | 90 |
| WAITING_REVIEW | 95 |
| DONE | 100 |

### 4.2 阶段进度

```text
stage_progress =
Σ(task_weight × task_progress) / Σ(task_weight)
```

任务权重优先顺序：估算工作量点数 > 预计工时 > 复杂度分 > 默认1。

阶段验收未通过时最高99%，只有阶段负责人确认完成后才为100%。

### 4.3 项目总进度

```text
project_progress = Σ(stage_weight × stage_progress)
```

推荐初始阶段权重：

| 阶段 | 权重 |
|---|---:|
| 需求澄清 | 15% |
| 信息架构/方案定义 | 20% |
| 方案深化 | 30% |
| 制作交付 | 25% |
| 验收归档 | 10% |

项目可自行配置权重，但合计必须为100%。所有百分比必须可展开查看计算明细。

### 4.4 AI执行进度

```text
run_progress =
Σ(已完成步骤权重)
+ 当前步骤权重 × 当前步骤内部完成度
```

模型调用无法可靠估计内部进度时，显示“第2/4步”以及不定进度动画，禁止伪造百分比。

### 4.5 项目健康度

```text
risk_score =
0.30 × schedule_deviation
+ 0.25 × blocker_severity
+ 0.20 × external_dependency_risk
+ 0.15 × critical_path_risk
+ 0.10 × capacity_risk
```

| 风险分 | 健康度 |
|---|---|
| 0～29 | 正常 |
| 30～59 | 有风险 |
| 60～100 | 需关注 |

强制升级规则：

- 关键路径任务逾期：至少“有风险”。
- 关键任务阻塞超过24小时：至少“有风险”。
- 关键外部依赖逾期且无替代路径：直接“需关注”。
- 项目负责人可人工覆盖，但必须填写原因、有效期并保留审计。

### 4.6 今日任务排序

```text
priority_score =
0.30 × deadline_urgency
+ 0.25 × business_priority
+ 0.20 × unblock_value
+ 0.10 × dependency_readiness
+ 0.10 × effort_fit
+ 0.05 × user_focus_match
```

规则覆盖：

- 已阻塞且用户无法自行解决的任务不排为“今天第一件事”。
- 等待外部默认移出主任务区。
- 待本人验收、待本人决策可进入高优先级。
- 用户手动置顶优先于算法，并记录置顶原因和有效期。

### 4.7 候选任务置信度

```text
candidate_confidence =
0.25 × task_evidence
+ 0.15 × evidence_completeness
+ 0.15 × owner_resolution
+ 0.10 × due_date_resolution
+ 0.10 × deliverable_resolution
+ 0.10 × project_resolution
+ 0.10 × extractor_agreement
+ 0.05 × source_quality
- ambiguity_penalty
- duplicate_penalty
```

同时保存标题、负责人、截止时间、项目、交付物、验收标准的字段级置信度。

阈值建议：

- `≥85`：正常进入人工确认队列。
- `60～84`：标注缺失/歧义字段，要求逐项确认。
- `<60`：进入低置信度队列，不主动通知被建议负责人。

阈值上线后必须用人工确认数据校准，不能长期固定。

### 4.8 重复任务检测

```text
duplicate_score =
0.25 × title_lexical_similarity
+ 0.35 × embedding_similarity
+ 0.15 × same_project_stage
+ 0.10 × owner_overlap
+ 0.10 × time_overlap
+ 0.05 × deliverable_similarity
```

- `≥0.85`：强提示重复。
- `0.70～0.84`：展示可能相关任务。
- `<0.70`：正常创建。
- 模型仅在中间区间做语义复核；是否合并由人决定。

### 4.9 负责人推荐

```text
assignee_match =
0.35 × skill_match
+ 0.20 × project_experience
+ 0.20 × available_capacity
+ 0.15 × historical_delivery_quality
+ 0.10 × deadline_feasibility
```

硬性排除：无权限、请假、负荷超上限、角色冲突、任务要求指定角色。

### 4.10 人员负荷

```text
capacity_load =
Σ(remaining_effort × urgency_factor × concurrency_factor)
/ available_work_hours
```

- `<70%`：可接受新任务。
- `70%～100%`：谨慎推荐。
- `>100%`：不默认推荐，除非负责人人工确认。

### 4.11 专家推荐

```text
expert_match =
0.35 × domain_match
+ 0.20 × similar_case_count
+ 0.20 × answer_quality
+ 0.15 × response_speed
+ 0.10 × current_availability
```

模型负责抽取问题领域和生成推荐理由，算法负责排名。

### 4.12 积分

积分必须由明确事件触发：

```text
TASK_COMPLETED          按任务预设积分
OPEN_TASK_COMPLETED     任务积分 + 5
HELP_RESOLVED           +5
KNOWLEDGE_PUBLISHED     +3
REUSABLE_SKILL_PUBLISHED 由管理员配置
```

AI不得根据“价值感”自由给分。重复事件使用幂等键防止重复积分。

## 5. 会议与聊天任务提取

### 5.1 会议链路

```text
会议开始/上传录音
→ ASR语音转写
→ 说话人区分与成员映射
→ 按议题和时间切片
→ T2识别行动项、决策、风险、待确认问题
→ T3生成会议纪要和结构化候选任务
→ 人员/项目/时间实体解析
→ 重复检测与字段置信度计算
→ 会议负责人统一审核
→ 正式分发
→ 被分配人确认接收/退回/改期
```

会议候选任务必须保存原始证据：

```text
meeting_id
transcript_segment_id
speaker_id
start_time_ms
end_time_ms
evidence_text
```

### 5.2 聊天链路

```text
连接器接收增量消息
→ 权限和可见范围校验
→ 按群、线程、回复关系和时间窗口聚合
→ 规则过滤纯表情、系统消息、无行动内容
→ T2批量判断是否存在任务
→ T2/T3抽取任务字段
→ 人员和项目映射
→ 重复检测
→ 来源负责人审核
```

不要逐条消息单独调用模型，应以“对话线程/上下文窗口”为单位批处理。

### 5.3 相对时间标准化

“今天、明天、本周五、月底”等时间先由时间解析器结合：

- 消息发送时间
- 用户时区
- 公司工作日历
- 节假日
- 上下文中明确日期

转换为绝对时间。模型可抽取原始表达，但最终时间由规则服务生成。

### 5.4 人员实体解析

解析顺序：

1. 明确的 `@成员ID`。
2. 会议说话人与账号绑定。
3. 通讯录姓名/别名精确匹配。
4. 项目成员候选集模糊匹配。
5. 模型结合语境判断。
6. 仍不明确则留空，禁止随意分配。

## 6. Embedding 与 RAG 规格

### 6.1 Embedding用途

- 语义搜索。
- 相似任务和重复任务召回。
- 相似求助和历史解决方案召回。
- 项目/阶段候选匹配。
- 专家能力文本与问题语义匹配。
- 知识聚类和标签建议。
- RAG第一阶段召回。

Embedding 不直接负责最终判断。

### 6.2 Embedding模型选型

至少评测以下指标：

- 中文语义召回率 Recall@10。
- 中英混合项目名称和专业词表现。
- 向量维度及存储成本。
- 单条和批量吞吐。
- 查询延迟。
- 私有部署或外部API的数据政策。

建议保留两档：

- `EMBED_FAST`：低维、低成本，日常索引和大规模召回。
- `EMBED_QUALITY`：高质量，用于重要知识和疑难查询。

Embedding版本必须写入每条向量；切换模型时后台重建索引，不可混用不同空间的向量。

### 6.3 切分策略

| 内容 | 切分方式 |
|---|---|
| 文档/知识页面 | 标题层级+段落，保留父级标题 |
| 会议 | 议题+时间段+发言人，保留原始时间戳 |
| 聊天 | 线程+回复链+时间窗口，不按单条消息切 |
| 任务 | 背景、目标、交付物、验收标准、结果分别索引 |
| 决策 | 独立决策条目，记录生效时间和决策人 |
| AI运行 | 最终确认产物可索引；中间草稿默认不进入正式知识 |

### 6.4 RAG检索链路

```text
解析问题
→ 权限过滤
→ 团队/项目/对象类型/时间元数据过滤
→ BM25关键词召回
→ Embedding语义召回
→ 合并去重
→ Reranker重排
→ 选择Top-K证据
→ 模型生成带引用答案
→ 记录引用与反馈
```

权限必须在召回前过滤，不能先召回敏感内容再让模型“不要显示”。

### 6.5 RAG答案规则

- 回答必须返回来源对象、标题、版本和原文片段位置。
- 没有可靠证据时明确说明“不足以回答”。
- 多来源冲突时列出冲突，不得擅自合并成确定结论。
- 业务状态、负责人、截止时间等精确字段优先查业务数据库，不通过向量库猜测。
- 已删除或失去权限的内容必须同步从索引删除或立即不可检索。

## 7. AI执行与Agent编排

### 7.1 AI执行生命周期

```text
任务确认
→ 选择AI/HYBRID和Agent
→ 权限与预算预检
→ 生成执行计划
→ 人工确认高风险计划（如需要）
→ 排队
→ 执行步骤
→ 工具调用与产物版本记录
→ 失败重试/等待输入
→ 提交AI结果
→ 人工确认
→ 业务验收
→ 完成或退回继续执行
```

### 7.2 Agent可写入范围

Agent默认可以：

- 读取授权项目和任务。
- 更新自己的运行子状态。
- 写执行日志。
- 上传临时产物。
- 请求人工输入。
- 创建候选任务。
- 提交结果等待确认。

Agent默认不可以：

- 直接完成业务任务。
- 修改项目权限。
- 删除正式资产。
- 修改积分。
- 将知识草稿直接发布。
- 把任务派给未授权成员。

### 7.3 失败分类

```text
TRANSIENT_NETWORK       临时网络失败，可自动重试
RATE_LIMIT              限流，退避重试或切换模型
MODEL_TIMEOUT           模型超时，可缩短上下文或切换模型
TOOL_ERROR              工具失败，按工具幂等规则重试
INSUFFICIENT_CONTEXT    信息不足，请求人工补充
PERMISSION_DENIED       权限不足，禁止绕过
BUDGET_EXCEEDED         超预算，等待人工批准或降级
QUALITY_GATE_FAILED     质量检查未通过，重新生成或转人工
UNSAFE_ACTION           高风险动作，停止并请求人工确认
```

### 7.4 幂等和可恢复

- 每次运行有 `run_id`。
- 每个步骤有 `step_id` 和 `idempotency_key`。
- 重试不得重复创建任务、发送通知或增加积分。
- 中间产物版本化保存。
- 人工停止后保留已完成步骤和产物。

## 9. 业务状态机和人工门禁

### 9.1 任务状态

```text
CANDIDATE
PENDING_OWNER_CONFIRMATION
TODO
IN_PROGRESS
WAITING_EXTERNAL
BLOCKED
WAITING_HUMAN_CONFIRMATION
WAITING_REVIEW
DONE
CANCELED
```

### 9.2 关键流转规则

- `CANDIDATE → TODO`：必须有候选审核通过记录。
- 会议任务正式下发后可先进入 `PENDING_OWNER_CONFIRMATION`。
- `IN_PROGRESS → WAITING_HUMAN_CONFIRMATION`：AI任务提交结果。
- `IN_PROGRESS → WAITING_REVIEW`：人工任务提交交付物。
- `WAITING_HUMAN_CONFIRMATION → WAITING_REVIEW/DONE`：必须由人确认AI结果。
- `WAITING_REVIEW → DONE`：必须由验收人通过。
- 任意执行状态转 `WAITING_EXTERNAL`：必须填等待对象、事项、跟进人和恢复动作。
- `DONE`后的修改必须创建新版本或重新打开，并记录原因。

### 9.3 人工审核SLA

建议默认：

- 候选任务：24小时。
- AI需要输入：4小时工作时间。
- AI结果确认：24小时。
- 关键任务验收：24小时。
- 知识发布审核：48小时。

超时只提醒或升级，不自动视为通过。

## 11. 性能、成本与质量目标

### 11.1 延迟目标

| 场景 | 目标 |
|---|---|
| 普通页面和统计 | P95 < 500ms |
| 关键词/向量搜索 | P95 < 1.5s |
| 聊天候选任务批量抽取 | P95 < 15s/批次 |
| AI对话首字响应 | P95 < 3s |
| RAG完整回答 | P95 < 12s |
| 会议纪要 | 会议结束后5分钟内进入审核队列 |
| AI Agent执行 | 异步，不阻塞页面；10秒内可看到运行状态 |

### 11.2 成本指标

至少监控：

- 单个候选任务平均AI成本。
- 单场会议转写和提取成本。
- 单次RAG问答成本。
- 单个AI执行任务成本。
- 每用户/团队/项目日成本。
- T2/T3/T4调用比例。
- 缓存命中率。
- 升级模型比例。
- 失败重试造成的额外成本。

建议初始路由目标：

- T0/T1完成的请求 ≥ 50%。
- 模型请求中 T2 占比 ≥ 60%。
- T4推理模型占比 ≤ 10%。
- 缓存可用场景命中率 ≥ 20%。

比例仅作为初始运营目标，不能为了省钱牺牲关键任务质量。

### 11.3 质量指标

| 场景 | 指标 |
|---|---|
| 任务检测 | Precision、Recall、人工确认率、遗漏率 |
| 字段抽取 | 标题/负责人/时间/项目/交付物字段准确率 |
| 去重 | 重复识别准确率、误合并提示率 |
| RAG | Recall@K、引用准确率、无证据拒答率 |
| 会议纪要 | 决策覆盖率、任务覆盖率、事实错误率 |
| 推荐负责人 | Top-3接受率、被退回率、负荷冲突率 |
| AI执行 | 人工确认通过率、退回率、重试率 |
| 求助 | 首次解决率、平均解决时间、知识复用率 |

## 12. 评测、反馈与持续优化

### 12.1 上线前评测集

必须从真实业务构建脱敏评测集：

- 不包含任务的普通聊天。
- 明确任务聊天。
- 多人、多任务、多人称代词的复杂聊天。
- 有相对时间和模糊时间的聊天。
- 有负责人但无交付物的聊天。
- 会议决策、风险、任务混合内容。
- 重复任务和相似但不重复任务。
- 有答案、无答案、资料冲突的求助。
- 有权限和无权限的RAG查询。

### 12.2 人工反馈闭环

以下操作自动形成训练/评测标签：

- 候选任务确认、修改、忽略。
- 修改了哪个字段。
- 关联了哪个重复任务。
- 接受或拒绝推荐负责人。
- AI答案是否解决。
- AI执行结果通过或退回。
- 退回原因分类。
- 知识草稿修改量。

未经评审的线上数据不能直接用于训练或自动调整规则。

### 12.3 Prompt和模型版本管理

- Prompt必须有版本号。
- 模型切换必须记录评测结果和灰度范围。
- 支持按团队或流量比例A/B测试。
- 关键场景先影子运行，不直接影响用户。
- 模型或Prompt升级后必须可回滚。

## 13. 安全、隐私与权限

- 所有数据必须带 `tenant_id`、`team_id` 和权限元数据。
- 个人AI会话默认仅本人可见；共享必须明确操作。
- 项目AI协作只检索当前项目授权内容。
- Agent使用短期Token和最小权限。
- 外部模型调用前执行数据分级和脱敏策略。
- 敏感客户资料可配置只允许内部模型处理。
- Prompt、日志和模型输出不得包含密钥、Token和不必要的个人信息。
- 权限撤销后，缓存、向量索引和Agent上下文必须同步失效。
- 所有人工审核、模型调用、工具调用和状态变化进入不可篡改审计日志。
- 防止提示词注入：RAG资料只能作为不可信数据，不能覆盖系统规则和工具权限。

## 14. 降级策略

| 故障 | 降级方式 |
|---|---|
| 模型服务不可用 | 保存原始内容，进入“待AI处理”队列；人工仍可手动建任务 |
| 推理模型超预算 | 降级通用模型并提示质量风险，或等待人工批准 |
| Embedding不可用 | 使用关键词搜索和元数据过滤 |
| Reranker不可用 | 使用BM25与向量加权排序 |
| RAG无结果 | 明确无证据，转人工或建议补资料 |
| ASR失败 | 允许上传文字纪要或重新转写 |
| 人员匹配失败 | 负责人留空，禁止猜测派发 |
| 时间解析失败 | 保留原文并要求人工选择绝对时间 |
| Agent工具失败 | 保存进度和产物，按幂等规则重试或转人工 |
| 通知服务失败 | 进入重试队列，不影响业务状态 |

任何降级都不能绕过人工门禁或权限。

## 16. 开发优先级

### P0：可信闭环

1. 核心数据模型和统一事件。
2. 权限、状态机、人工审核和审计。
3. 任务/阶段/项目进度算法。
4. 绝对时间、提醒和等待外部规则。
5. Model Gateway、调用日志和预算控制。
6. 聊天/会议候选任务提取。
7. 候选任务人工确认和来源证据。
8. 基础Embedding、混合搜索和权限过滤。
9. AI执行状态、日志、人工确认与验收。

### P1：智能协作

1. 项目健康度和风险解释。
2. 今日任务排序。
3. 重复任务检测。
4. 推荐负责人和开放任务。
5. 智能求助、专家路由和知识草稿。
6. 个人AI助手和项目AI协作。
7. Skill运行和知识发布流程。

### P2：学习与自动化

1. 基于反馈的排序和置信度校准。
2. 延期预测和容量预测。
3. 明确低风险规则下的自动创建。
4. 模型自动路由优化。
5. 私有小模型蒸馏或微调。

在真实人工反馈不足前，不建议微调模型，也不建议开放无确认自动派发。

## 17. 验收清单

### 17.1 人工门禁

- [ ] 候选任务未经审核不能成为正式任务。
- [ ] AI结果未经确认不能进入业务完成。
- [ ] 验收只能由指定验收人或授权角色完成。
- [ ] 知识草稿未经审核不能发布为正式知识。
- [ ] 高风险Agent动作不能绕过权限和人工确认。
- [ ] 所有人工决定可追溯。

### 17.2 算法

- [ ] 项目百分比可展开到阶段、任务和检查点。
- [ ] 阻塞和等待外部不会伪造进度。
- [ ] AI运行百分比来自实际步骤。
- [ ] 风险健康度有计算明细和触发规则。
- [ ] 推荐结果能说明主要匹配因素。
- [ ] 积分具备幂等性，不会重复发放。

### 17.3 AI/RAG

- [ ] 抽取结果通过JSON Schema校验。
- [ ] 候选任务保留原始证据。
- [ ] RAG回答有引用且遵循权限。
- [ ] 无证据时不会编造答案。
- [ ] 不同模型可以通过配置切换。
- [ ] 小模型失败或低置信时可升级模型。
- [ ] 每次调用可查询模型、版本、成本和延迟。

### 17.4 性能与成本

- [ ] 页面统计不依赖实时模型调用。
- [ ] 聊天按线程批处理而非逐条调用。
- [ ] 支持缓存、异步队列和限流。
- [ ] 支持用户/项目/团队预算。
- [ ] 模型失败有降级方案。

### 17.5 安全

- [ ] 项目和个人AI上下文严格隔离。
- [ ] Agent权限最小化。
- [ ] 权限撤销后向量和缓存立即失效。
- [ ] 外部模型调用遵循数据分级和脱敏。
- [ ] RAG内容不能通过提示词注入扩大工具权限。

## 19. 最终实施原则

本系统的“AI原生”不等于“所有事情都交给AI”，而是：

```text
AI负责理解、检索、生成和执行；
算法负责计算和排序；
规则负责边界和一致性；
数据负责事实；
人负责判断、授权、验收和发布；
平台负责让整个过程可控、可追溯、可降级、可评测、可控制成本。
```

开发实现时，如某个场景无法明确回答“谁拥有最终决定权、结果来自什么数据、如何计算、何时调用模型、失败如何降级、成本如何记录”，则该场景尚未达到可上线标准。
